#### Description

##### 1. プロジェクト背景とPoCの立ち上げ
自社CRMプロダクトにおける生成AI/LLMの活用可能性を探索するため、フィージビリティ検証からスタートしました。当初は具体的な機能要件が固まっていなかったため、CRMの強みである顧客データを活かした「顧客セグメンテーションの自動化」や「自然言語クエリによるデータ分析」などのPoCを推進しました。

##### 2. 技術選定とプロトタイピングの変遷
- **PoCツールの選定と移行**:
  - 検証速度を最優先し、まずはローコード/GUIプラットフォームである **Dify** を採用して迅速なプロトタイプを構築。

  - 顧客セグメンテーションの自動化機能。
  - メールおよびLINE配信文面の自動生成機能。
  - 複雑なRAG（検索拡張生成）構成を最初から組み込むのではなく、まずは外部コンテキストなしの洗練されたプロンプトエンジニアリングをベースに「シンプルかつ早期に価値を届ける」ことを最優先してプロトタイプを完成させました。

##### 3. ビジネスサイドとの合意形成と協業体制の確立
生成AIに対する過剰な期待（「AIを導入すれば全自動で成果が出る」「Biz側で開発し、エンジニアはセキュリティチェックのみでよい」といった風潮）に対し、以下の組織的アプローチで現実的な協業体制へと導きました。
- **あえてBiz側へ開発環境を提供**:
  - 頭ごなしに否定するのではなく、Bizメンバーが実際に開発・検証できる環境を整備して提供。実用レベルのプロンプト作成やエッジケース対応の難しさを現場で直接体感してもらいました。
- **役割分担の是正**:
  - 結果としてBiz側がエンジニアリングの専門性の必要性を理解し、「Biz側が顧客目線でのユースケースやデザインモックを提案し、エンジニア（自身）が主導して本格的な設計・実装を推進する」という建設的なパートナーシップへと軟着陸させました。

##### 4. 成果と得られた学び・知見
- **ビジネス目線でのプロジェクト推進力**:
  - Bizサイドと密に連携しながら唯一の専任エンジニアとしてプロジェクトを主導したことで、「Bizがいつまでに何を必要としているのか」「マーケティングや告知のタイミングをどう合わせるか」といったビジネス要求を深く理解し、プロダクトマネジメント視点を持った開発推進力を体得しました。
- **基礎技術の深掘りに対する教訓**:
  - トレンド変化が激しいAI領域において、組織調整だけでなく、RAG、ガードレール、ナレッジグラフ、プロンプトキャッシング等の基礎技術のPoCをより深く先行して自らの手で検証し続ける重要性を再認識しました。

### CDP・DWH プロジェクト

#### 基本情報

- 役割: テックリード（実質）

Go, gRPC, Echo, GORM, protovalidate, dockertest, OpenTelemetry, AWS SQS, Aurora PostgreSQL, Apache Spark, S3 Tables (Apache Iceberg), Jupyter Notebook, (AWS StepFunctions), (AWS Glue DataBrew), Python

#### Description

##### 1. プロジェクトの背景と課題の本質（「Easy」が招いたComplexの打破）
- **プロジェクトの変遷**:
  - 当初は既存プロダクトのDB改修（テナントごとに分離されたDBを単一DBに集約し、社内横断分析からインサイトを得る）程度のものでした。しかし、競合他社が一般的なCDP・データ基盤機能を導入し始めたことに追従するため、本格的なデータ基盤サービスへと舵を切ることになりました。
- **従来の「筋の悪い」設計の打破**:
  - それまでのプロダクトは、特殊な分析要望ごとに個別機能を開発し、最終的には「ユーザーの要求に応じて弊社エンジニアがSQLを作成し定期実行する」という有料オプション機能を作るなど、極めて硬直的で使いづらい構造に陥っていました。
  - これは「ユーザー視点」に固執して何でもお膳立てしようとした結果、**「Easyness（手軽さ）」を追求しすぎてシステムが「Complex（複雑怪奇）」化**していたのが本質的な原因でした。
- **提案と方針転換の主導**:
  - 「ユーザーに不要な制約を課す厚いラッピングを排除し、ユーザー自身が直接クエリを実行でき、テーブルを作成できるようにする」という本質的でシンプルな方針を提案。エンジニア全員での議論によるデザイン悪化を打破し、当時のマネージャーの強い後押しを得て方針採択を勝ち取りました。このアプローチにより最短で高い価値を提供できる基盤を確立し、後に会社から表彰を受けました。

##### 2. アーキテクチャ設計思想：「正しさが先、パフォーマンスは後」
- **データ規模**:
  - 最大で数百万件程度、大半は数十万件規模のテナントが約250テナント。
- **設計思想（Correctness First）**:
  - 早期の過剰な最適化（premature optimization）による設計の崩壊を徹底して避け、**「ドメインモデルを正しくコードに反映する（正しさが先）」**ことを最優先としました。
  - パフォーマンスのボトルネックが判明した段階で、必要に応じて設計を崩す（チューニングする）アプローチを採用。
- **OpenTelemetryによる可観測性の確保**:
  - 上記の判断を勘ではなくデータに基づいて下すため、**OpenTelemetry (OTel)** を全面導入して分散トレーシングとメトリクスによる徹底した可観測性を構築しました。

##### 3. OSS（`containerd`）から学んだ現実的なモジュラモノリス
- **教条主義・原則主義からの脱却**:
  - 過去にDDDやクリーンアーキテクチャの厳格な原則適用でうまくいかなかった反省や、原則に従うことに拘泥する周囲のエンジニアを反面教師とし、「原則に固執せず、自らの感覚を信じて柔軟に設計する」スタンスへ転換しました。
- **モジュラモノリスの実装**:
  - `containerd/nerdctl` へのOSSコントリビューション経験を通じ、`containerd/containerd` の堅牢なコードベースを読み込んでいた知見を活かしてアーキテクチャを設計。
  - Go + gRPCによるAPIバックエンドと非同期ジョブワーカーからなるシステムをゼロベースで開発し、高い保守性と拡張性を確立しました。
- **タグベース管理の導入（DockerおよびObsidian思想の反映）**:
  - テーブルに属性を付与する仕組みとして、硬直化しやすい階層的（ディレクトリベース）な分類を廃し、**「タグベース（属性ベース）の管理」**を採用しました。
  - これはDockerのコンテナ・ラベル管理やObsidianのタグ管理思想に着想を得たものであり、SSOプロジェクトで痛感した「ディレクトリベース管理は前提の変化に弱く筋が悪い」という教訓が直接活きた設計判断でした。これにより、要件変化に極めて柔軟なメタデータ管理を実現しました。

##### 4. 次世代データ基盤（EMR Spark + S3 Tables / Iceberg + Jupyter）の設計と推進
- **成熟したエコシステムへの着目**:
  - 自社独自の仕組みを再発明するのではなく、成熟したオープンなデータ基盤技術にシフトすべきと判断。自主的に調査を行い、上長への相談や勉強会を通じてチームへナレッジを共有しました。
- **アーキテクチャの検証**:
  - **AWS EMR (Apache Spark) + S3 Tables (Apache Iceberg) + Jupyter Notebook (AWS ECS)** を組み合わせた次世代データ基盤を設計し、実装を進めました（会社の状況変化により最終的に中断したものの、最先端のOpen Table Formatを用いたモダンデータスタックのPoC・設計を完遂）。

##### 5. チームリーダーシップと上位職エンジニアとの協業術
- **チーム体制の変遷**:
  - 当初は自身と元々のCDP設計者である上位職エンジニアの2人体制（主導は自身）でスタートし、初期リリース後は6人体制へと拡大。ジュニアメンバーのメンター・技術指導を担当しました。
- **上位エンジニアへのアプローチ**:
  - 職位が上のエンジニアに対して設計を伝える際、過剰に手取り足取り教えるのではなく、あえて「自分で考えてもらう」突き放しを交えたコミュニケーションを採ることで自立と納得を促し、良好な協調関係を構築しました。
- **技術的イニシアチブの確立**:
  - 本プロジェクトを通じて「社内で最も高い技術力を持つエンジニア」としての確固たる信頼を確立し、以後のプロジェクト推進をスムーズに行える土台を築きました。

### シングルサインオン (SSO) プロジェクト

#### 基本情報
- 期間: 2021-10-01 ~ 2026-10-31
- 役職: エンジニア
- 役割: 主担当
- 規模: 1人

#### 技術スタック
Keycloak, OpenID Connect (OIDC), OAuth2.0, Go, TypeScript, AWS Lambda, AWS VPC, AWS ALB, AWS ECS, AWS Route53, Laravel

#### Description

##### 1. プロジェクトの発端：マルチプロダクト化と「CSV同期」への警鐘
- **背景**:
  - 当時、社内で「マルチプロダクト化（既存CRMの巨大な機能を分解して新規プロダクトとして切り出す構想）」が進行していました。
- **課題と問題提起**:
  - 当初進みかけていた設計は「各プロダクトが個別にユーザー管理・認証機能を持ち、プロダクト間でユーザー情報をCSV出力して同期する」という、極めて非効率かつセキュリティ・整合性リスクの高いものでした。
  - これに対し「ユーザー管理と認証は中央に集約すべき」と根本的なアーキテクチャの是正を提言。その結果、認証統合基盤の担当を任されることになり、さらにユーザー体験向上の観点からシングルサインオン（SSO）を導入する全社プロジェクトとして始動しました。

##### 2. 技術選定の経緯と反省（マネージド vs OSS自前運用）
- **標準規格の採用**:
  - 拡張性、セキュリティ、ナレッジの汎用性を重視し、標準規格である **OpenID Connect (OIDC)** および **OAuth 2.0** を全面採用。
- **Keycloak自前運用の選定理由と反省**:
  - AWS Cognitoなどのフルマネージドサービスを使わなかった理由は、「ユーザー情報を外部マネージドサービスに任せたくない」という経営層の判断によるものでした（DBとしてAurora PostgreSQLを使う以上実質的な差異は少なかったものの、当時はその判断を受け入れ、ECS上でOSSの **Keycloak** を自前構築・運用する方針となりました）。
  - インフラ運用負荷や保守コストの観点から、振り返ればフルマネージドの採用をより強く提言すべきであったという教訓を得ました。

##### 3. 全社横断プロジェクトにおけるコミュニケーションと推進の学び
- **社内コンテキストに合わせたドキュメント化**:
  - OAuth 2.0 / OIDCは概念が抽象的であり、外部の良質な解説記事を紹介してもチームメンバーにはなかなか読まれませんでした。
  - そこで、世間的な新規性はなくとも「自社のサービスやアーキテクチャの文脈に落とし込んだ社内向け解説ドキュメント」を自ら執筆したところ、メンバーにしっかりと読まれ理解が進みました。「ドキュメントの価値は新規性ではなく、自社の共通言語で書かれていることにある」という重要な気づきを得ました。
- **オピニオネイテッド（Opinionated）な推進**:
  - 各サービス担当者の個別の要望に合わせて調整を重ねようとすると議論が発散・停滞するため、「基盤側が明確な指針・標準仕様（取り決め）を決定し、強い方針（Opinionated）を持って提示する」ことこそが、全社横断プロジェクトをスムーズに完遂させるために不可欠であると学びました。

##### 4. アーキテクチャ設計における反省と教訓（変化への適応と「Easyness」の罠）
- **前提変化に耐えうるデータ設計**:
  - 当初の認識に基づいて階層的なディレクトリベースでユーザー管理を設計したものの、事業の進展とともにマルチプロダクト化の前提自体が大きく変化し、構造が硬直化してしまいました。「タグベース（属性ベース）のフラットな設計にしておけば、より柔軟に変化に対応できた」という設計上の深い学びとなりました（この教訓は、後にDWHプロジェクトにおけるテーブル属性のタグベース管理へと活かされることになります）。
- **不要な自前ユーザー管理アプリの開発（Easynessの再発）**:
  - 「Keycloakの標準管理画面は社内運用者にとって難しい」という理由から、別のシニアエンジニアの主導でKeycloakのラッパーとなるユーザー管理アプリを別途自作することになりました。
  - これはCDP・DWHでの反省と同様、「Easyness（手軽さ・お膳立て）を求めて自前でラッピング層を作った結果、かえってシステムがComplex（複雑・保守困難）化する」という典型例でした。当時は全体を俯瞰してこれを制止するに至らなかったという反省があり、以後の「シンプルさを最優先する」設計思想の確立につながりました。
